## 3. Objective

Introduce the tenant-scoped customer identity and customer financial account aggregate required by Epic 39.

This story creates the account foundation only. It must not introduce store credit balances, ledger rows, refund issuance, redemption, loyalty points, accounting events, or customer merge behavior.

## 4. User Story

As a tenant administrator,
I want customer financial accounts linked to tenant-scoped customer identities,
so that later store credit and loyalty ledgers have a stable, auditable owner without storing mutable wallet balances on the customer record.

## 5. Locked Decisions

1. `CustomerFinancialAccount` is the aggregate root for future customer value movement.
2. A minimal tenant-scoped `Customer` identity record is required because the current codebase has refund customer-reference fields but no reusable customer model.
3. One customer may have at most one active financial account per tenant.
4. A customer financial account uses one immutable `currency_code`.
5. Account ownership is immutable after creation.
6. Account states are `active`, `suspended`, and `closed`.
7. `closed` accounts cannot be reactivated in Story 39.1.
8. `suspended` accounts remain inspectable but cannot redeem value in later stories.
9. Story 39.1 does not create ledgers, balances, projections, outbox events, or reports.
10. Customer merge is out of scope and must not be simulated by reassigning account ownership.
11. Customer deletion/anonymization must preserve future financial references.
12. `Customer.status` represents identity lifecycle only.
13. `CustomerFinancialAccount.status` represents financial-account lifecycle only.
14. IDs are generated by the application and must never be accepted from client requests.
15. Display names are search/display fields only and must never be treated as stable identifiers.

## 9. Data Model

### 9.1 `customers`

Purpose:

Tenant-scoped customer identity record used by financial accounts and later customer-facing features.

Recommended columns:

```text
id UUID PRIMARY KEY
tenant_id UUID NOT NULL
display_name STRING NOT NULL
normalized_display_name STRING NOT NULL
email STRING NULL
phone STRING NULL
external_reference STRING NULL
status STRING NOT NULL DEFAULT active
metadata JSON NULL
anonymized_at TIMESTAMP NULL
created_by UUID NULL
updated_by UUID NULL
created_at TIMESTAMP
updated_at TIMESTAMP
deleted_at TIMESTAMP NULL
```

Recommended indexes and constraints:

```text
INDEX tenant_id, status
INDEX tenant_id, normalized_display_name
INDEX tenant_id, email
INDEX tenant_id, phone
UNIQUE tenant_id, external_reference WHERE external_reference IS NOT NULL where supported
FOREIGN KEY tenant_id -> tenants.id
```

Notes:

1. Use soft deletes if the project convention is needed for historical-reference safety.
2. `email` and `phone` are lookup fields, not verification guarantees.
3. Do not require email or phone. Walk-in customer accounts may start with display name only.
4. Do not store payment credentials or sensitive identity documents.
5. If the database cannot support partial unique indexes consistently, enforce optional external-reference uniqueness in request validation and service code.
6. `Customer.status` is the customer identity lifecycle, not the financial-account lifecycle.
7. Email uniqueness is not required per tenant. Shared household emails, shared business emails, and walk-in records must be allowed.
8. `metadata` is an extension point only and must not store balances, loyalty points, ledger state, or payment credentials.
9. Customer IDs are application-generated UUIDs and are not accepted from client request payloads.

### 9.2 `customer_financial_accounts`

Purpose:

Tenant-scoped aggregate root for future store credit and loyalty ledgers.

Recommended columns:

```text
id UUID PRIMARY KEY
tenant_id UUID NOT NULL
customer_id UUID NOT NULL
status STRING NOT NULL DEFAULT active
currency_code STRING NOT NULL DEFAULT tenant currency
opened_at TIMESTAMP NOT NULL
suspended_at TIMESTAMP NULL
closed_at TIMESTAMP NULL
created_by UUID NULL
updated_by UUID NULL
created_at TIMESTAMP
updated_at TIMESTAMP
```

Recommended indexes and constraints:

```text
INDEX tenant_id, status
INDEX tenant_id, customer_id
UNIQUE tenant_id, customer_id
FOREIGN KEY tenant_id -> tenants.id
FOREIGN KEY customer_id -> customers.id RESTRICT
```

Rules:

1. `currency_code` defaults to `Tenant.currency`.
2. `currency_code` is immutable after creation.
3. `customer_id` is immutable after creation.
4. No balance columns are allowed.
5. No ledger sequence columns are needed in this story; those belong to Story 39.2.
6. Tenant currency is resolved at account creation time and snapshotted on the account.
7. Later tenant currency changes must not rewrite existing customer financial accounts.
8. `CustomerFinancialAccount.status` is the financial lifecycle and must not be inferred from `Customer.status`.
9. A customer must not be physically deleted after a financial account exists. Use anonymization or soft deletion instead.

## 10. Models

Create:

1. `app/Models/Customer.php`
2. `app/Models/CustomerFinancialAccount.php`

Model requirements:

1. Use `HasFactory`, `HasUuids`, and `BelongsToTenant`.
2. `Customer` has one `CustomerFinancialAccount`.
3. `CustomerFinancialAccount` belongs to `Customer`.
4. `CustomerFinancialAccount` belongs to `Tenant`.
5. Guard against direct mutation of `customer_id` after creation.
6. Guard against direct mutation of `currency_code` after creation.
7. Provide constants for account statuses:

```text
STATUS_ACTIVE = active
STATUS_SUSPENDED = suspended
STATUS_CLOSED = closed
```

8. Provide query scopes for active/suspended/closed if useful, but do not add balance methods.

## 11. Service Layer

Create:

```text
app/Services/Customers/CustomerFinancialAccountService.php
```

Responsibilities:

1. Create a customer if needed.
2. Create the customer financial account.
3. Lookup accounts by account ID or customer ID.
4. Suspend an account.
5. Reactivate a suspended account.
6. Close an account.
7. Anonymize customer personal fields while preserving stable references.
8. Emit audit events for lifecycle mutations.

Future ownership note:

Story 39.1 may let `CustomerFinancialAccountService` create the minimal customer identity needed for account setup. Future customer-management stories may extract broader customer lifecycle behavior into a dedicated `CustomerService`; in that future shape, `CustomerFinancialAccountService` should orchestrate account creation rather than own all customer behavior.

Service rules:

1. All mutations run inside database transactions.
2. Tenant context is required.
3. Account creation validates that the customer belongs to the active tenant.
4. Account creation rejects duplicate account creation for the same customer.
5. Suspension is allowed only from `active`.
6. Reactivation is allowed only from `suspended`.
7. Closure is allowed from `active` or `suspended`.
8. Reactivating `closed` is prohibited.
9. Ownership reassignment is prohibited.
10. Currency changes after creation are prohibited.
11. Display-name lookup is search only and must not be used as identity.
12. Client-provided IDs are ignored or rejected for create requests.
13. Existing accounts block customer hard deletion.

Recommended domain errors:

```text
CustomerFinancialAccountAlreadyExistsException
CustomerFinancialAccountStateConflictException
CustomerFinancialAccountOwnershipImmutableException
CustomerFinancialAccountCurrencyImmutableException
```

If the codebase does not yet have a domain-exception mapping layer, controllers may map these exceptions to `409` JSON responses directly.

## 14. Request Validation

Create request classes as needed:

```text
app/Http/Requests/Customers/StoreCustomerFinancialAccountRequest.php
app/Http/Requests/Customers/UpdateCustomerFinancialAccountStatusRequest.php
app/Http/Requests/Customers/AnonymizeCustomerRequest.php
```

Store request fields:

```text
customer_id nullable uuid exists customers,id
id prohibited
display_name required_without customer_id string max:255
email nullable email max:255
phone nullable string max:32
external_reference nullable string max:100
currency_code nullable string size:3
metadata nullable array
```

Status update request:

```json
{
  "status": "suspended",
  "reason": "Customer requested temporary hold"
}
```

Allowed status payloads:

```text
active
suspended
closed
```

Validation rules:

1. `reason` is required for suspension and closure.
2. `reason` is optional for reactivation but should be accepted.
3. `currency_code` defaults to the tenant currency and must match the tenant currency in Story 39.1 unless an explicit multi-currency decision is approved later.
4. Customer lookup fields must be tenant scoped.
5. Client-provided `id` values must be rejected.
6. `display_name` filtering is search-only and must not resolve a unique customer by itself.

## 15. Audit Events

Use `AuditLogger`.

Required audit actions:

```text
CUSTOMER_CREATED
CUSTOMER_UPDATED
CUSTOMER_ANONYMIZED
CUSTOMER_FINANCIAL_ACCOUNT_CREATED
CUSTOMER_FINANCIAL_ACCOUNT_SUSPENDED
CUSTOMER_FINANCIAL_ACCOUNT_REACTIVATED
CUSTOMER_FINANCIAL_ACCOUNT_CLOSED
```

Audit payload requirements:

1. Include customer ID.
2. Include customer financial account ID where applicable.
3. Include status before/after for lifecycle transitions.
4. Include currency code.
5. Include actor.
6. Include reason for suspension and closure.
7. Do not include full sensitive personal data in metadata if a masked or field-name-only payload is sufficient.
8. Personal data should be masked or omitted; audit entries should favor identifiers and field names over raw values.

## 21. Review Decisions

1. Branch Manager receives `customer-accounts.view` only in Story 39.1. `customer-accounts.manage` stays Owner/Admin-only.
2. API-first implementation is acceptable and preferred for the first PR if it keeps scope focused. A minimal Inertia page may be included only if it stays limited to create, view, and lifecycle actions.
3. `external_reference` should be unique per tenant where the database supports partial unique indexes. If not portable, enforce uniqueness in service validation.
