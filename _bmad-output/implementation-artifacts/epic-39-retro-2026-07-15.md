## 3. What Went Well

1. The Epic 38 documentation hierarchy scaled well into Epic 39.
2. The architecture lock and implementation guide kept financial invariants visible throughout the epic.
3. Store credit was correctly treated as monetary liability rather than a casual customer balance field.
4. The append-only ledger model gave refund issuance, redemption, review, and reporting a stable base.
5. Idempotency, drift detection, source evidence, and accounting handoff were treated as core requirements rather than late hardening.
6. The implementation sequence was strong: customer account, ledger, refund issuance, redemption, review, loyalty planning, reporting.
7. Reporting surfaced reconciliation exceptions instead of attempting automated repair.
8. CI and PR cadence improved during the epic, with green checks used as a merge gate.

## 4. What Was Difficult

1. Story status drift accumulated across documentation layers.
   This was corrected during closeout by marking store-credit runtime stories as `Done`, then later by marking Story 39.9 as the loyalty runtime completion story.

2. Loyalty status needed clarification.
   Story 39.6 and 39.7 are now recorded as specification-complete, with runtime execution completed by Story 39.9.

3. ADR maturity is uneven.
   The ADR index exists, but several ADR files are still placeholders while ADR-039 is approved.

4. Reporting exposed hidden dependency truth.
   Story 39.8 made the loyalty implementation gap visible because it had to report both store-credit and loyalty activity.

5. BMad sprint tracking does not include Epic 39.
   `_bmad-output/implementation-artifacts/sprint-status.yaml` only tracks earlier epics, so Epic 39 closeout had to rely on the implementation-plan docs and Git history.

## 5. Key Lessons

1. Documentation status should be updated in the same PR as implementation completion.
   The guide, story file, ADR index, and README should not be allowed to drift.

2. "Plan approved" and "code implemented" need separate status labels.
   This is especially important when a branch contains a story specification but not runtime code.

3. Report stories are good readiness auditors.
   Reconciliation and reporting work naturally exposes missing source evidence, placeholder domains, and status inconsistencies.

4. Monetary ledgers need conservative boundaries.
   Store credit benefited from strict separation between account identity, ledger posting, refund authority, payment authority, and reporting.

5. Placeholder ADRs are useful early, but should be finalized or explicitly labeled as deferred before epic closeout.

## 10. Retrospective Verdict

Epic 39 was a strong execution step for customer financial accounts and store credit. It successfully extended the Epic 38 architecture pattern into another major subsystem and produced a safer ledger-based foundation for refunds, redemption, review, and reporting.
