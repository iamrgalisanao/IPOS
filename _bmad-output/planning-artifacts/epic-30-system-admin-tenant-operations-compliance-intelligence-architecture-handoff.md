## 2. Proposed Epic

Epic 30 — System Admin Tenant Operations & Compliance Intelligence

Goal:
Move beyond Epic 29 provisioning readiness into operational intelligence for System
Admins. The epic should improve visibility into tenant compliance detail, blocker
urgency, operational health, and admin review workflows without reopening tenant
creation, pilot enablement, subscription billing, POS checkout, offline sync, GCT,
Z-read, e-journal, receipt, or tax engine behavior.

---

## 3. Recommended Story Sequence

### 30.1 — Compliance Detail Drill-Down

Planning intent:
- Expand readiness visibility from aggregate pass/fail checks into explainable
  per-check detail.
- Show which tenant, branch, admin, profile, or compliance requirements are missing,
  incomplete, or pending.
- Provide remediation guidance for System Admin review.

Boundary:
- Read-first visibility slice.
- No automatic remediation.
- No BIR/CPA certification claims.
- No receipt, tax, GCT, Z-read, or e-journal engine changes.

### 30.3 — System Admin Operational Dashboard

Planning intent:
- Provide a System Admin dashboard for tenant readiness, blockers, pilot status,
  sign-off history, and operational review queues.
- Prioritize scanability and repeat admin workflows over marketing-style visuals.

Boundary:
- Dashboard and reporting only unless a later story explicitly approves mutation.
- No changes to tenant self-service UI unless separately approved.

### 30.2 — Tenant Risk Scoring and Deadline Urgency

Planning intent:
- Add a conservative operational risk score or urgency band based on existing
  blockers, blocker age, readiness state, and known review deadlines.
- Surface days-to-action style indicators where the underlying data is reliable.
- Display risk and urgency in the operational dashboard rather than creating a
  standalone scoring surface first.

Boundary:
- Advisory only.
- No auto-suspension.
- No automatic feature disablement.
- No billing or subscription enforcement changes.

### 30.4 — System Admin Persona-Based Views

Planning intent:
- Evaluate whether platform support should remain one broad role or split into
  personas such as account manager, compliance officer, and operations reviewer.
- Define least-privilege access expectations before implementation.

Boundary:
- Architecture and permission design first.
- No migration of existing platform support users until approved.

### 30.5 — Optional Hardware Readiness Tracking

Planning intent:
- Evaluate whether POS device or machine profile operational readiness should appear
  in System Admin visibility.
- Keep this optional because IPOS intentionally supports offline operation.

Boundary:
- No hardware sync as mandatory blocker unless separately approved.
- No offline sync/posting changes.
- No POS checkout behavior changes.

Architecture sequencing decision:
30.1 should ship first because it is read-only and unlocks explainable readiness.
30.3 should follow before 30.2 so risk/urgency has a stable dashboard surface. 30.4
remains design-first until a least-privilege mutation need is proven. 30.5 remains
optional and should wait until dashboard usage shows whether hardware readiness is a
useful System Admin signal.

## 4. Recommended Architecture Review Questions

1. Which capabilities belong in Epic 30 versus later operational analytics work?
2. Should compliance detail be stored as persisted check records or derived from
   existing tenant, branch, user, and machine profile data?
3. Should risk scoring be computed on request, cached, or generated by a scheduled job?
4. Which risk indicators are objective enough to show without creating false
   compliance claims?
5. Do System Admin personas require new roles, new permissions, or only filtered views?
6. What is the minimum dashboard surface needed before optional hardware readiness is
   worth designing?
7. Which items require mutation-boundary approval before implementation?
